Animal Shelter Dashboard

Description of the artifact

The artifact that I chose for the database category is my Animal Shelter Dashboard from CS 340: Client/Server Development. The project was originally made in the Computer Science program with Python, MongoDB, PyMongo, Dash and Jupyter Notebook. The dashboard connects to Austin Animal Center data and allows a user to filter animals based on different rescue needs. It also shows the results as a table, a breed chart and a map.

I decided to utilize this project since it already showed I could connect an application to a database and do CRUD activities, but it also had various areas that might be enhanced. The initial version worked for the assignment but some of the database code was created more for the sake of getting the required functionality to operate. For CS 499 I went back and looked at it more carefully in terms of security, validation, error handling, and maintainability.

Why I chose this artifact and what I did better

I added this artifact to my ePortfolio because a large amount of real software development includes database work. Most apps rely on data that's persisted somewhere. So building the interface is only part of the process. The program also need a database layer that is reliable, intelligible, and adequately secure.

One of the main adjustments I made was to get rid of the MongoDB username and password that were hardcoded in the notebook. The improved version reads the database credentials from environment variables. This is a preferable habit as credentials should not be saved in source code, especially if the project is uploaded to GitHub or shared with other individuals.

I also refactored the AnimalShelter CRUD class. The earlier version validated against certain empty values but took a very large range of input with little validation and caught every exception in the same way. In the improved version, the CRUD methods verify if the queries and records are dictionaries before passing them to MongoDB. I also modified the error handling to catch PyMongo database failures directly. This makes the code clearer because programming flaws will be less likely to be masked as database connection difficulties.

The read technique was extended to support projections, sorting and limit the results. I also implemented methods for counting records, testing the MongoDB connection and for properly quitting the database client. These improvements increase the re-usability of the class and also add functionality that may be valuable as the dashboard grows.

On the dashboard side I put the rescue filters into one RESCUE_QUERIES dict instead of constructing almost the same query structure in multiple distinct if statements. This makes the filter logic much easy to read and update. I also implemented more robust handling of empty results and invalid lat/lon values so the map doesn't presume every entry has useable coordinates. Also cleaned up the pie chart logic to calculate the breed numbers before building the chart.

Overall I think the artifact is stronger with the enhancements, because the improvements are not simply visible. The biggest differences are in the way the software interfaces with MongoDB and the way it handles data, failures, configuration and future changes. The dashboard accomplishes the same fundamental task, but under the hood the code is better structured and more amenable to further improvement.

Learning Objectives

This improvement reflects the course outcomes I sought to address in Module One. The most powerful relationship is the result of using sound methodologies, skills and tools to build computing solutions that deliver value. The project employs a combination of Python and MongoDB to turn the data of shelters into something that a user can actually search and comprehend on the dashboard.

It also confirms the finding on designing and evaluating computing solutions through computer science methods and standards. I had to look at the original design, see what portions were tougher to maintain and update the structure without destroying the objective of the program. Examples of this are moving the rescue queries into one place and making the CRUD class more reusable.

The security mentality result was more essential in this upgrade than it was in the initial project. A few modest modifications, like removing hard coded credentials, verifying inputs, and being more careful with database problems are indicative of how I would like to approach a real application. I don’t think this one item defines all the parts of the security outcome, but it does indicate movement toward security as a design and not an afterthought.

My general strategy of outcome coverage has not altered significantly. I still think that the three artifact categories are good to work with because they demonstrate distinct aspects of my experience in computer science. This artifact of database provides me more tangible evidence of client/server development, database design, security configuration and maintenance of an existing software.

Discussion of the Improvement Process

The biggest thing I learnt about this change is that code can be functional and still have a lot of potential for improvement. The first goal for this project was to connect to MongoDB, have the filters return the correct animals, and make sure everything is displayed appropriately on the dashboard. Later, looking at it again, there were problems that I hadn’t paid as much attention to the first time.

The hard programmed login info was a nice example. It was fun when I was working on the original task, but not something I would want in a project that others might view. Changing that made me think more about the distinction between code that is suitable for a fast class exercise and code that is more like a professional practice .

Another difficulty was how much to alter the project. The milestone’s purpose is to demonstrate how I improved an existing item, and I did not want to fully replace the original work. I wanted to really modify things, but still keep the dashboard recognizable. That means greater attention to the database layer, validation, query organization and error handling, instead of revamping the complete interface.

I also discovered that maintainability comes from typically pretty basic choices. Consolidating the rescue queries. Clearer responsibilities for the database methods. Checking inputs before operations. Adding re-usable options to the read function. All of these make the project easier to understand. The improvements don’t totally rewrite the application, but they do make the code cleaner and easier to work with.

I feel more comfortable with the project today than I did when I originally created it since I can see not just how the database connection works, but why certain design decisions are better than others. This improvement allowed me to take the lessons I have learnt from CS 340 and make the project a better representation of my current skillset.
