CS 499 Milestone Two: Software Design and Engineering Enhancement

Savanna Neace

Description of the Artifact

For my software design and engineering enhancement, I chose the Inventory Tracking App that I worked on in CS 360: Mobile Architecture and Programming. The original project was an Android Studio application written in Java. It already had screen layouts for tasks like viewing inventory and adding items, but the starter code did not connect those screens into a complete application. I thought this made it a good project to revisit because I could keep the original purpose while showing how much my approach to software development has improved.

The goal of the app is straightforward: allow a user to keep track of items and their quantities in one place. For this enhancement, I turned the basic interface into a more organized application with account registration, sign-in, persistent inventory records, and the ability to add, edit, delete, and search items. I also included optional low-stock text alerts. These features gave me room to work on code organization, validation, user experience, and security rather than only changing the appearance of the screens.

Why I Selected It and What I Improved

I included this artifact because Android development brings together several areas that are important in software engineering. A user might only see a few buttons and text fields, but a useful application also needs to handle input safely, save information reliably, and recover from ordinary situations like closing and reopening the app. In the original version, most of that work still needed to be done. The enhanced version provides a clearer example of how I can take an unfinished prototype and develop it into a maintainable software project.

One important change was separating inventory rules from the Android screens. I added an InventoryRules class that decides whether an item is valid, whether its quantity counts as low stock, and when a low-stock alert should be triggered. Keeping this logic separate makes it easier to understand and test without starting the whole Android application. I wrote JUnit tests for empty names, negative quantities, the low-stock boundary, and the difference between entering low stock for the first time and repeatedly editing an already-low item.

I also improved how inventory information is accessed. The SQLite database stores records for individual users, and the item queries are limited to the signed-in user. I added search by item name using SQL selection arguments rather than inserting user-entered text into a query. The search handles characters such as percent signs and underscores as literal search text. I also added an index for owner and item name, along with a versioned database upgrade that preserves existing data. These choices make the project easier to extend and help avoid problems that would come from recreating the database during every update.

Beyond the database and code structure, the app has a clearer flow from login to inventory management. Users can edit or remove items, and deletion requires confirmation. Registration stores a salted password-derived hash rather than plain-text passwords. Optional SMS alerts are kept separate from inventory features, so declining SMS permission does not stop users from managing their items. These details matter because reliability and security are part of the application design, not extra features to consider after coding.

Course Outcomes and Skills Demonstrated

This enhancement most directly supports the course outcome about applying appropriate techniques, skills, and tools to develop computing solutions that provide value. I used Java, Android Studio project conventions, SQLite, and automated unit tests to build an application around a real inventory-management task. It also supports the outcome about evaluating solutions with computer science principles. Separating business rules from interface code and adding focused database queries required me to think about maintainability, correctness, and design trade-offs.

The security outcome is also represented through password hashing, record ownership checks, parameterized queries, and optional permission handling. I would not describe this class project as production-ready security, but it demonstrates the direction I want to continue taking: think about how data is protected while designing the system. The code comments, README, and tests also support professional communication by explaining what the application does and how someone else can review it. My overall plan for covering the remaining outcomes stays the same: the Treasure Hunt project demonstrates algorithms and data structures, while the Animal Shelter Dashboard demonstrates database design and client/server development.

Reflection on the Enhancement Process

The biggest lesson for me was that making a program more complete is not the same thing as just adding more code. At first, it was tempting to put everything inside an activity because that seemed faster. Once the inventory rules, persistence, and notifications were involved, it became much easier to reason about the project when each part had a clear responsibility. The standalone rules class is a small change, but it made the expected behavior easier to explain and allowed me to check several important cases with unit tests.

Another challenge was thinking through what should happen when the user enters unexpected values or changes existing data. For example, an inventory item should never have a negative quantity, and a low-stock notification should not be sent every single time an already-low item is edited. Search input also needs to be treated as data instead of executable SQL. Working through these cases made me pay more attention to how features interact, not just whether each button responds.

I kept the original project alongside the enhanced version so it is possible to see what changed. I was able to compile the independent InventoryRules Java class in the preparation environment, but I could not run an Android emulator or complete a full Gradle build there. That still needs to be tested in Android Studio, including database upgrades and SMS permission behavior, before I can describe the app as fully verified. I think this is an important part of being professional with software: explaining what has actually been checked, and being clear about what remains.

Overall, this artifact shows my growth from creating an Android interface to thinking more carefully about the structure behind it. The enhancements made the application more useful, but they also gave me practice writing testable logic, preserving data, keeping users separated, and documenting decisions. Those are skills I want to continue applying to larger software projects after graduation.
